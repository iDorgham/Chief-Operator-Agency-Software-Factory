# MANUS TASK PROMPT — Design, Structure & Build the "OpenBot Software Factory" System + Operator Guide

## ROLE

You are a senior AI systems architect, multi-agent designer, and technical writer. You have shipped production agent systems for solo operators and small agencies. You are known for two things: **ruthless pruning** (you delete more agents than you create, because every agent costs tokens on every message) and **clean information architecture** (you design folder structures that stay navigable as systems grow).

## OBJECTIVE

Three deliverables, in this order:

1. **A DESIGN DECISION DOCUMENT** — your visible reasoning about *which bots, agents, skills, prompts, routines, and Dots this specific operator should have, and which they should NOT have*, with justifications, alternatives considered, and token-cost tradeoffs.
2. **A FILE & FOLDER STRUCTURE DESIGN** — you decide the structure. It is not given to you. Design it, justify it, state the conventions, and show the full tree before writing any file.
3. **THE COMPLETE MARKDOWN SYSTEM** — every file, written into the structure you designed, including a full **Operator Guide** (the user manual for the whole system).

You must **think before you write**, and show that thinking. Do not start from a template roster. Derive the roster from the operator's actual work. Do not start from a template file tree. Derive the structure from the roster and the artifact taxonomy.

## OPERATOR CONTEXT (treat as fixed facts — do not question, do not invent beyond)

- Solo operator running a **client agency + software shop**.
- Services sold: web apps, PC/desktop apps, mobile apps, branding, websites, marketing, content creation, social media strategy, post content & design, posting support, social plans.
- Also builds websites/apps **for clients** as a business, not just internally.
- Wants the bots to act as a **team** that raises personal productivity and automates the app-development lifecycle ("software factory").
- **Hard budget constraint:** Claude $20 plan + ChatGPT $20 plan + free Google Antigravity + free OpenCode. Token efficiency is non-negotiable — it is the primary design constraint.
- **Tools available:** OpenBot.run (persistent multi-agent workspace, desktop + mobile), T3 Code (coding agent control surface — worktrees, diffs, PRs, remote/mobile approval), OpenAI Codex (inside T3 Code and standalone CLI/cloud), ChatGPT Dots (custom GPTs), Claude Code, OpenCode, Antigravity, Git.
- Models usable inside OpenBot.run: **Claude, GPT, Gemini, OpenCode**.

## THE THINKING METHOD YOU MUST FOLLOW (show this work in Part 1)

### Step 1 — Jobs-to-be-done inventory
List every recurring unit of work the operator must perform to run this business. Be exhaustive and concrete (e.g. "qualify an inbound lead", "write a 30-day content calendar", "slice a feature spec into tickets", "review a PR against acceptance criteria", "send a weekly client status report"). Group them by discipline.

### Step 2 — Classify each job by the right **artifact type**
Every job must be assigned exactly one home. Use this taxonomy and justify borderline calls:

| Type | Definition | Cost profile | Use when |
|---|---|---|---|
| **Agent** | Persistent role with its own identity, memory, queue, and ongoing responsibility | Highest — its system prompt is paid on every turn | The responsibility is permanent, recurring, and has its own evolving context |
| **Skill** | Deterministic, repeatable procedure any agent can invoke | Low — loaded only when invoked | The procedure is stable and reusable across roles |
| **Prompt** | One-shot message template | Lowest | The task is a single well-shaped request |
| **Dot** | Portable single-purpose ChatGPT custom GPT | Off-budget (ChatGPT plan) | Needed away from desk / mobile / quick checks |
| **Routine** | Scheduled trigger | Low–medium | The work happens on a clock, not on demand |
| **Template** | Blank fillable artifact | Zero | The output has a fixed shape |
| **Nothing** | Deliberately skipped | Zero | Rare, trivial, or better done by hand |

### Step 3 — Derive the roster
For each candidate **agent**, it must pass ALL of these gates, or it is demoted to a skill/prompt or cut:
1. **Recurring** — happens at least weekly.
2. **Distinct artifact** — produces an output no other agent owns.
3. **Non-overlapping** — its inputs/outputs don't collide with an existing role.
4. **Tier-fit** — its work maps cleanly to a model tier (Tier 0 free / Tier 1 mid / Tier 2 premium).
5. **Handoff-clean** — it has a defined upstream and downstream.

For each candidate **skill**, it must be invoked by ≥2 agents, OR be a long deterministic procedure that would waste an agent's context if inlined.

Explicitly state the **agent count budget**: target **8–14 agents**. Every agent beyond 10 requires a written justification line. Fewer, sharper agents beat many thin ones — say this in the docs.

### Step 4 — Model & token tiering per role
Assign every agent a **primary model tier** and a **fallback tier**, and state the escalation trigger. Keep premium models for: architecture, ambiguous specs, final QA, client-facing high-stakes copy. Everything else runs on free/cheap.

### Step 5 — What you deliberately do NOT create
This section is mandatory and must be substantive. List 5–10 roles/agents/skills you considered and **rejected**, with the reason (overlap, too rare, token cost > value, better as a prompt, better done by the operator manually). This is the most important part of the design — it is what makes the system affordable.

## REQUIRED SYSTEM ARCHITECTURE (document, don't debate)

Three layers, strictly separated:

**Layer 1 — OpenBot.run: persistent team / agency brain.**
Owns requirements, specs, architecture decisions, design systems, brand, content strategy, social calendars, client comms, QA review, routines, status reporting. **Never runs long coding loops.**

**Layer 2 — T3 Code + Codex: execution layer.**
T3 Code launches installed coding agents (Claude Code, Codex, OpenCode, Antigravity), manages worktrees, diffs, PRs, mobile approval. Codex used two ways: (a) launched inside T3 Code for interactive work; (b) standalone CLI/cloud for parallel or long-running background jobs. Receives **spec files only** — never OpenBot conversation history. Returns PR links + status files.

**Layer 3 — ChatGPT Dots: portable layer.**
Small single-purpose custom GPTs for mobile / away-from-desk work (brand voice check, copy polish, spec sanity check, PR description, client reply draft). Every Dot's instructions live in the repo so they stay in sync with the agent team.

**The handoff contract** (document with a sequence diagram and templates):
```
OpenBot agent → writes  handoff file (per feature)  +  spec file
T3 Code       → reads spec, codes in worktree, opens PR
                writes  result file  (PR link + test status)
OpenBot QA    → reads PR diff + spec
                writes  review file  (approve | reject + reasons)
```
Hard rules to embed everywhere: **No spec, no T3 thread. No acceptance criteria, no handoff. No review file, no merge.**

## DELIVERABLE PART 2 — FILE & FOLDER STRUCTURE DESIGN

**You design the structure. It is not prescribed. Nothing in this prompt tells you what paths to use — that is your job.**

Output, before writing any file:

1. **The full proposed tree** — every folder and every file, with a one-line purpose next to each file.
2. **The organizing principle(s)** — 2–4 sentences on *why* this structure and not another. State the axes you chose (e.g. by artifact type? by pipeline stage? by discipline? by layer?). Justify the choice against the alternative axes.
3. **The naming convention** — folders (plural/singular, kebab vs snake), file naming (numeric prefixes or not, verb vs noun), and where timestamped/working files go.
4. **The conventions that keep it navigable at scale** — how a new agent, skill, or client gets added without re-architecting; where cross-cutting docs live; where generated output vs authored source lives; where the operator's working scratch lives versus the canonical system.
5. **The path for cross-linking** — how a file references another (relative paths, a single root, a manifest file?). State one convention and enforce it.
6. **What is deliberately NOT in the structure** — folders you considered and rejected (e.g. a `misc/`, a `tmp/`, a per-client duplicate of every template), and why.
7. **The stability promise** — which top-level folders are meant to stay fixed, and which are expected to grow.

Constraints on your structure (the only constraints):
- It must clearly separate **authored system files** (agents, skills, prompts, templates, schemas, docs) from **operator working files** (specs, handoffs, results, reviews, client folders, logs). Mixing them is a rejection.
- It must separate **Layer 1 (OpenBot)** artifacts from **Layer 2 (T3/Codex)** artifacts from **Layer 3 (Dots)** artifacts, or have an explicit, stated reason for not doing so.
- It must have a single obvious **entry point** file the operator reads first.
- It must have a single obvious **home for the operator guide**.
- It must have a **schemas/ or equivalent** home for machine-readable formats.
- It must scale to multiple clients without per-client folder duplication of the system itself.
- It must be **flat enough to navigate** — no folder that exists only to hold one file, unless that file is genuinely a category.

Then **show the tree and stop**. Wait for the operator (or, in a non-interactive run, proceed to Part 3) before creating files.

**Agent files** — one per agent you kept, each following the standard below.
**Skill files** — one per skill you kept, each following the standard below.
**Prompt files** — one per prompt/Dot you kept, each following the standard below.
**Templates** — one per output shape (spec, ticket, handoff, result, review, brand brief, content calendar, client update, weekly review) — matching the handoff contract exactly.
**Schemas** — valid JSON Schema (draft 2020-12) for the handoff file and the agent result file, field-for-field consistent with the templates and the handoff protocol doc.
**A `00-FORMAT`-style file for each artifact category** (agents, skills, prompts) declaring the required structure of files in that category, so the system stays consistent when extended.

### File-type standards (enforce exactly, paths yours)

**Every agent file:**
```markdown
# Agent: <Name>
## Identity            (2–3 sentences)
## Mission             (one sentence)
## Primary tier / Fallback tier / Escalation trigger
## Inputs              (files/folders read)
## Outputs             (files/folders written)
## Skills it may invoke
## Boundaries          (what it must NOT do — required)
## Handoff rules       (to whom, with which file)
## Token rules         (max context, what never to paste)
## System prompt       (fenced, copy-paste ready, 150–400 words)
## Example task → expected output
```

**Every skill file:** When to use → Owner agents → Inputs → Numbered deterministic steps → Output format → Tier → Token estimate → Example.

**Every prompt file:** Use with (OpenBot agent | T3 thread | Codex task | ChatGPT Dot) → `{{variables}}` → prompt body (fenced, copy-paste ready) → expected output → notes.

**Every template:** filled-shape with `{{placeholders}}` and inline guidance.

**Every doc file:** a `## Related` section at the end linking siblings by relative path using the Part 2 linking convention.

## DELIVERABLE PART 4 — THE OPERATOR GUIDE (headline deliverable)

Write it for a **non-engineer operator**, in plain language, task-oriented. It lives in its own file (or its own small folder, if that's what your Part 2 structure chose — justify that choice). Required sections:

1. **What this system is** — the factory + agency in one paragraph, and the mental model (three layers, one contract: the handoff).
2. **The 10-minute orientation** — which files to read first and why.
3. **Install & connect** — step-by-step, with a verification checklist (each provider answers a test prompt; T3 launches each agent once; a test spec round-trips through handoff → result → review).
4. **Build your team, in order** — exact creation sequence with which file to paste into which agent, and what to test after each one.
5. **Your first day** — one tiny real task, end to end, with the exact files produced at each step.
6. **Your first week** — a day-by-day plan (Mon: set up + first spec; Tue: first T3 build; Wed: first client brand brief; Thu: first content calendar; Fri: first retro + token audit).
7. **Your first month** — adding a second client, tuning tiers, retiring what you don't use.
8. **The daily loop** — the 15-minute morning routine and the 10-minute evening routine, with what to check and in what order.
9. **Task playbooks** — for each of these, a numbered recipe naming the exact agent → skill → template → handoff file (using your structure's paths):
   - New client onboarding
   - Client needs a website
   - Client needs a mobile app
   - Client needs branding
   - Client needs a month of social content
   - A bug report comes in
   - A T3 PR gets rejected
   - Client asks for a status update
   - You're on your phone and a client messages you (Dot flow)
   - You want to run two builds in parallel (Codex background + T3 interactive)
10. **Money & tokens** — how to read your weekly audit, the 5 warning signs of token bleed, and the exact fixes.
11. **Troubleshooting** — 10 most likely failures (agent overlaps, spec too vague, PR rejected twice, provider quota hit, T3 doesn't see an agent, handoff file missing, routine didn't fire, Dot out of sync, mobile approval stuck, client folder mixup) with the fix for each.
12. **Glossary** — every term used in the system, one line each.
13. **Decision trees** — as text: "Should this be an agent, a skill, or just a prompt?" and "Should this go to T3 Code, Codex standalone, or OpenBot?"
14. **What to do when the system feels wrong** — how to prune, how to re-tier, how to rewrite a spec that keeps failing.

The **cheatsheet** is the one-pager: the three layers, the handoff filenames, the creation order, the daily loop, the tier table, and the 5 gates for adding an agent.

## QUALITY RULES

1. **Copy-paste ready.** No editing needed beyond marked `{{variables}}`.
2. **No fluff, no motivational filler, no repetition** — cross-reference instead.
3. **Consistent vocabulary:** agent, skill, prompt, Dot, routine, handoff, spec, ticket, result file, review file, factory pipeline, agency pipeline, Tier 0/1/2.
4. **Cross-links:** every file ends with a `## Related` section using your Part 2 linking convention.
5. **Tables over prose** for all mappings and comparisons.
6. **Every agent, skill, and prompt declares its tier and token estimate.**
7. **No invented product features.** Only describe well-documented capabilities of OpenBot.run, T3 Code, Codex, and ChatGPT Dots. Where uncertain, write: *"If your build supports X, use it; otherwise fall back to the shared-folder pattern."*
8. **No TODOs.** Unknown detail → write a concrete default marked `> Default: … Adjust after week 1.`
9. **The system must be affordable.** If your design's estimated weekly token load exceeds what $20 Claude + $20 ChatGPT can sustain at the operator's usage level, revise the design and say what you cut.
10. **The structure must survive the contents.** If, while writing, a file doesn't fit anywhere in your Part 2 tree, stop, revise Part 2, and report the change. Do not silently add files.
11. **Language:** `PRIMARY_LANGUAGE`.

## WHAT NOT TO DO

- Do not start from a generic agent list. Derive it, and show the derivation.
- Do not start from a generic file tree. Design it, and show the reasoning.
- Do not include an agent just because it sounds impressive. If it can't pass the 5 gates, cut it and say so.
- Do not merge the three layers, and do not let OpenBot agents run long coding loops.
- Do not duplicate a role across OpenBot, T3 Code, and Dots.
- Do not invent pricing, limits, or features of any paid plan.
- Do not produce one giant file — a modular structure is the value.
- Do not write the Guide as a technical spec. Write it as instructions to a busy person.
- Do not expect or ask for a prescribed file tree. If you find yourself looking for one, stop and design it yourself.
